# Decisions — VVU Campus Safety App

Record of choices the proposal left open. Update this file when something changes, and tell Claude Code to read it before assuming.

## Decided

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| D1 | MVP scope | Build the 4.2 functional requirements + Chapter 1 objectives. Visitor, vehicle, key, patrol and shift-handover modules (Ch3, 4.1) are **Phase 2**. | They aren't in 4.2's requirements; not enough time before December. |
| D2 | ID verification | Seed an `idRoster` collection from a Registry/HR CSV; `verifyId` function checks it at registration. | Makes "student ID authentication" real and testable. |
| D3 | Who gets SOS alerts | All officers with `onDuty == true` (no "nearest officer" routing). | Simpler and reliable on one campus; "nearby" needs constant officer tracking. |
| D4 | Direct communication | In-incident chat + "Call security" button. | Covers Obj ii with no extra infrastructure. |
| D5 | Evidence media | Photos only (max 3, ≤ 1 MB each after compression). No video in MVP. | Storage cost, upload time on mobile data. |
| D6 | Admin dashboard | Flutter Web from the same codebase, hosted on Firebase Hosting. | One language, shared models. |
| D7 | Password security | Firebase Authentication handles password hashing and storage. No custom hashing. | Industry-standard; describe it this way in the thesis. |
| D8 | Roles | Firebase custom claims set only by Cloud Functions. | Clients can't escalate their own role. |
| D9 | Status enum | `new`, `alerted`, `accepted`, `on_scene`, `resolved`, `false_alarm`. Reporter cancel = `resolved` + `cancelledByReporter: true`. | Small, testable state machine. |
| D10 | State management / routing | Riverpod + go_router. | Common, well-documented, testable. |
| D11 | Location tracking | Only during an active SOS; stops when closed. | Privacy and battery. |
| D12 | Project location | The Flutter project lives at the repo root (`campus-security/`), package `gh.edu.vvu.vvu_campus_safety`, created with `--project-name vvu_campus_safety .` | Keeps `CLAUDE.md` and `docs/` beside the code, as the repo layout expects. |
| D13 | Local Firebase project | Develop against the emulator-only project `demo-vvu-campus-safety` (`.firebaserc` default). `lib/firebase_options.dart` holds demo values until `flutterfire configure` replaces it; the real project is the `prod` alias. | The emulators run "demo-" projects with no login or real project, so work can start before the Blaze project exists. |
| D14 | Firebase client config in git | `firebase_options.dart` / `google-services.json` are committed. Service accounts and the SMS key (Functions secret) are never committed. (Maps need no key since D50.) | Firebase client keys only identify the project; access is enforced by security rules and API key restrictions. |
| D15 | Brand colours | VVU blue `#003A70`, gold `#F2B417`, SOS red `#C62828`; buttons at least 56 dp tall. | Approximate brand colours — swap in official hex values when the brand guide is available. |
| D16 | Rules before M1 | `firestore.rules` and `storage.rules` deny all client access until Milestones 1 and 3. | Safe default; nothing is readable by accident. |
| D17 | Functions test library | `firebase-functions-test` not installed yet: its peer range stops at `firebase-admin` 13 and we use 14. M1 tests the pure `roster.ts` logic with `node:test` and the rules with `@firebase/rules-unit-testing`, or add it when it supports admin 14. | Avoids `--force` installs. |
| D18 | Name check in `verifyId` | The roster surname (last word of `fullName`) must appear among the words the user typed, ignoring case, order and hyphens. The `users` doc stores the roster name, not the typed one. Unknown/inactive IDs are rejected before the name check; "already claimed" only after it. | PRD asks for a case-insensitive surname match; this tolerates first/last name order and reveals less about IDs someone guesses. |
| D19 | Failed registration | The app creates the Auth account, calls `verifyId`, and deletes the account if verification fails. If the delete fails, the user is still signed in but unverified and the router shows a "Verify your VVU ID" screen to retry. `verifyId` is idempotent for the same uid. | Meets "no usable account" without a server-side registration endpoint. |
| D20 | Profile fields users may edit | Rules use an allowlist: `phone` (+233 format) and `fcmTokens`; officers also `onDuty`. Deactivated users can't edit. | Safer than the denylist in the ARCHITECTURE outline — new fields are protected by default. |
| D21 | Role homes and platforms | Mobile: student/staff → `/home`, officer and admin → `/officer`. Web: admin → `/dashboard`, everyone else → "use the mobile app". Self sign-up link hidden on web. | ARCHITECTURE §1: web is admin-only; admins can do everything officers can. |
| D22 | Deactivated users | The app watches `users/{uid}.deactivated`; when true it signs out and shows why on the login screen. Auth `disabled` (set by `adminSetRole`) blocks new sign-ins with the same message. | Covers both a live session and later log-ins. |
| D23 | Push addresses | firebase_messaging 17 deprecates FCM tokens in favour of Firebase Installation IDs (`register()` / `onRegistered`). The app stores the FID in the existing `users.fcmTokens` array; functions send with `sendEachForMulticast({ fids })` and remove IDs FCM reports as stale. Push is mobile-only; the web dashboard uses live Firestore listeners. | Follows the current SDK without renaming a field in the schema. |
| D24 | SOS without GPS | Location is fetched while the countdown runs; after it ends the app waits at most 3 s more, then sends with `location: null` if there is no fix. Live tracking fills `lastLocation` as soon as a fix arrives. | "SOS must never be blocked" — a late location beats a late alert. |
| D25 | Active SOS screen | The member home *becomes* the active SOS screen while the user has an open SOS (one at a time), and location streams for as long as it is shown. Offline is detected from Firestore's `hasPendingWrites`; writes wait at most 6 s for the server, then stay queued. | Simple lifecycle: tracking can't outlive the SOS, and the offline card appears without a connectivity package. |
| D26 | Onboarding | Permissions screen shown once per device after first sign-in on mobile (`shared_preferences`). Declining never blocks; the home screen shows a "location off" card with a fix button. | PRD: handle denial gracefully with a clear explanation. |
| D27 | Timeline events | `onIncidentCreated` writes the `created` and `alerted` events (so offline SOS creation is a single write). Clients may only write events for their own actions: reporters `cancelled`; officers `accepted`, `assigned`, `on_scene`, `note`, `resolved`, `false_alarm`. | Keeps system events trustworthy. |
| D28 | Rules test project | Rules tests use project `demo-vvu-rules-test` and run serially, so they can run against the dev emulators without wiping dev data. | Lets tests run while the app demo is up. |
| D29 | Photo access | Each photo carries custom metadata `reporterId`; `storage.rules` lets that user and officers read it, with no Firestore lookup. `mediaUrls` stores Firebase download URLs, which are only visible to people who can already read the incident. Uploads are create-only (no overwrite or delete), images only, < 2 MB. | ARCHITECTURE §6 offered this option; it keeps Storage rules simple and evidence tamper-proof. |
| D30 | Report submission order | The app picks the incident id, uploads the compressed photos under `incidents/{id}/`, then writes the incident. Photo upload needs a connection (clear error if not); the document write itself queues offline like SOS. | Photos are optional; a report with photos must not point at files that don't exist. |
| D31 | "My reports" | Lists all the user's incidents, SOS alerts included, newest first. Report descriptions must be 10–1000 characters, enforced in the form and in `firestore.rules`. | One place to follow up on anything you raised. |
| D32 | Who may change status | On scene and resolve: officers in `assignedTo`, or any admin. False alarm: anyone on the security team. Assign adds to `assignedTo` and never removes. Closed incidents can't be edited by clients. Enforced in `firestore.rules` and mirrored by `IncidentRepository.canActOn`. | ARCHITECTURE §4 says "assigned officer/admin" for on scene and resolve. |
| D33 | Chat access | Any officer/admin and the reporter can read and write an incident's chat (not only the assigned officers), so a colleague can step in. Messages are permanent, in the sender's own name and role, text ≤ 2000 characters or a photo. | Simple, matches the ARCHITECTURE rules outline. |
| D34 | Chat pushes | A reporter's message goes to the assigned officers, or to everyone on duty if nobody is assigned yet. Security's message goes to the reporter. | Someone always hears the reporter. |
| D35 | Chat photos | Stored beside the incident's photos as `incidents/{id}/chat_{messageId}.jpg`, tagged with the incident's `reporterId`; officers may upload them (storage.rules). | Reuses one Storage rule so the reporter and officers can both open them. |
| D36 | Announcements | Users read only their own audiences (`all` + their group; admins everything), enforced in rules, so the app queries with `audience in [...]`. Pushed to the matching FCM topic on a separate, less urgent `announcements` Android channel. Chat and announcements use shared routes (`/chat/:id`, `/announcements`) open to every signed-in phone user; data access is still decided by the rules. | Matches the four topics devices already subscribe to. |
| D37 | Admin-created accounts | `adminCreateUser` makes officers and admins only (students and staff self-register against the roster). The admin sets a temporary password (≥ 8 characters) and hands it over; the person changes it with "Forgot password". The email is marked verified because the admin vouches for it. | No email service needed in the MVP; Firebase still hashes the password. |
| D38 | Role changes and deactivation | `adminSetRole` sets the claim, then `users.role`; the app sees the profile's role differ from its token and refreshes the token, so the new home screen applies within seconds. Deactivating sets `deactivated`, disables the Auth account and revokes refresh tokens. Admins can't change or deactivate their own account. Each change writes one `auditLogs` entry. | Avoids a waiting period of up to an hour for the token to expire, and stops the dashboard being locked out by accident. |
| D39 | Roster import | The dashboard parses the CSV (`idNumber,fullName,type,department[,active]`, optional header, quoted fields) and previews it; `adminImportRoster` re-validates each row, skips bad or repeated rows with a reason instead of failing the whole file, and merges into `idRoster` so `claimedBy` survives a re-import. Up to 5000 rows per call; the app splits larger files. | One typo shouldn't block a 3000-line Registry export. |
| D40 | Live board numbers | Summary cards are computed in the app from incidents raised in the last 7 days plus the open incidents. "Today" is the Accra (UTC) calendar day. "Resolved today" counts resolutions by security, not "I'm safe" cancellations, among incidents from the last 7 days. Average response uses `responseSeconds`. | No extra aggregation function; exact enough for a campus's volume. |
| D41 | New-SOS alarm | The dashboard sounds three beeps (Web Audio, no sound file) and flashes a red banner on every page when an SOS that nobody has accepted appears after the page loaded. SOS alerts already open at load are listed but don't sound. The banner clears when the SOS is accepted, opened or dismissed. | PRD §4.8 audible/visual cue without a push on the web (D23). |
| D42 | Incidents table and panel | The table shows the 300 most recent incidents, filtered in the app (open/closed, type, category, search). Any incident opens a side panel with details, the officer actions (admins can do all of them, D32) and the chat. Older incidents are for the analytics pages (Milestone 6). | Keeps the query to one simple index-free read. |
| D43 | Heatmap drawing | The heatmap groups incident locations into ~50 m squares and draws a circle per square, larger and redder with more incidents (tap for the count). Google's JavaScript heatmap layer is deprecated and being retired, so it isn't used. | Works the same on web and Android, and the grouping is easy to explain and test. |
| D44 | Analytics data | The page loads incidents raised in the chosen date range (whole Accra days, at most 5000) and applies the category filter in the app; SOS alerts are their own "SOS" category. Weeks run Monday–Sunday. The CSV export is exactly the filtered list, UTF-8 with a BOM for Excel, with spreadsheet formulas neutralised. | One range query with no composite index; the export matches what the charts show. |
| D45 | Emergency contacts | Private to the user (not even officers can read them). On SOS, `onIncidentCreated` texts up to 5 valid +233 numbers with the user's name and a Google Maps link, after alerting officers; an SMS failure never affects the alert. Until a gateway is chosen (O2) `ConsoleSmsProvider` logs the messages. | PRD §4.10; privacy of family numbers. |
| D46 | Settings changes | `settings/app` can no longer be written by clients; the settings page saves through `adminUpdateSettings`, which validates every field and logs which fields changed. Boundary and zones are edited as text, one point or zone per line. | Keeps the audit log complete; text editing avoids a map-drawing tool for the MVP. |
| D47 | Backups | `scheduledBackup` exports the whole database daily at 02:00 Accra time to `backups/YYYY-MM-DD` in the default bucket, retrying twice. | PRD §4.12. |
| D48 | Demo data | `npm run seed:demo` writes 120 closed incidents over the last 12 weeks to the emulator, weighted towards the hostels and lecture halls at typical hours, with full timelines and realistic response times (SOS faster than reports). Ids start with `demo-` and the random numbers are seeded, so re-running rewrites the same data. Reporters are made-up `demo-reporter-N` uids with no accounts. | Gives the heatmap and charts something meaningful for the demo and screenshots without touching real data. |
| D49 | Accessibility | Text colours meet WCAG AA (4.5:1), checked by `test/core/contrast_test.dart`; VVU gold is never used for text on white (dark amber `inProgress` instead). The SOS button and countdown work at 200% system text size; the countdown digit itself isn't scaled further. Buttons stay at least 56 dp high. Widget tests run at 360 dp width (small Android phones). | Users may be stressed, on small phones, or use large text. |
| D50 | Maps: OpenStreetMap instead of Google Maps | The four in-app maps (live board, analytics heatmap, incident map, report pin) use `flutter_map` with OpenStreetMap tiles, replacing `google_maps_flutter` from the original stack. Tiles come from `tile.openstreetmap.org` with the app's package name as user agent, and every map shows the required "© OpenStreetMap contributors" credit. The report pin moves by tapping (no dragging); dashboard pins open the incident on click. Turn-by-turn directions and SMS links still open Google Maps by plain URL, which needs no key. | Google Maps needs a billing account (card) for an API key; OSM needs neither, so the project can run at no cost. The OSM tile policy allows light use like a campus pilot; a larger roll-out should switch to a commercial or self-hosted tile server (only `osmTileLayer()` changes). |
| D51 | Dashboard design | The web dashboard has its own theme (`AppTheme.dashboard()`, used only when `kIsWeb`): a navy sidebar with pages grouped as Operations, People and System; flat white cards with thin borders on a light grey canvas; denser 44 px controls (the phone keeps 56 px touch targets); status, type and role shown as tinted pills. Shared pieces (`PageHeader`, `SectionCard`, `StatCard`, `EmptyState`, `Pill`) live in `features/admin/widgets/`. The ID roster page offers a downloadable sample CSV (`sampleRosterCsv`). `dashboard_pages_test.dart` opens every page at desktop and laptop sizes, with and without data, and fails on any error or overflow. | Supervisors use it on a computer for long periods; one consistent layout makes it quicker to read, and the sample file removes guesswork about the CSV format. |
